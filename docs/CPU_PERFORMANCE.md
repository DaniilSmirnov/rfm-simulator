# Лимит 60 FPS и снижение нагрузки на CPU

С 2026-10-08 `application/run/max_fps` равен 60 для всех сборок.
Это верхний предел; на 60 FPS весь кадр должен укладываться в 16.67 мс.
Повышение лимита с 24 до 60 вызывает покадровые функции до 2.5 раза чаще,
но не означает пропорционального роста всей нагрузки.
Управление машиной интегрируется шагами 1/120 с, сетевой sync — раз в 0.1 с.
Эти частоты не изменены. Проверки физики при 24, 60 и 144 FPS и prediction прошли.

## Измеренный исходный уровень

Godot 4.4.1 Linux, headless, лесной СУ, одиночная игра, без нажатых кнопок.
После генерации мира: 30 кадров прогрева и 300 замеров по 1/60 с для каждого
режима, с переходом к следующему кадру между замерами. Игра ещё в countdown:
активных боевых машин нет. Значения из одного запуска, не обещание FPS устройства.

| Блок | За рулём, среднее / p95, мс | Пешком, среднее / p95, мс |
|---|---:|---:|
| `game._process` целиком | 7.92 / 11.33 | 11.47 / 15.42 |
| Движение игрока | 1.40 / 2.49 | 0.68 / 1.21 |
| HUD | 0.09 / 0.22 | 4.74 / 6.82 |
| Камера | 0.07 / 0.16 | 0.02 / 0.07 |

В режиме пешком HUD составляет около 41% среднего времени `_process`.
Остаток включает зрителей, предметы, звук и другие вызовы; он не измерен
по отдельным блокам. Небольшие числа для racers/stones в countdown не
характеризуют нагрузку во время гонки.
Замер не включает GPU, весь SceneTree, физический сервер или выполнение WASM.
Нужны отдельные прогоны Android/iOS VK WebView, всех СУ, гонки и комнаты с 8 игроками.

Повторить (аргумент — индекс СУ: 0 лес, 1 зима, 2 деревня):

```sh
godot --headless --path game --script res://tools/profile_cpu.gd -- 0
```

Инструмент не включается в обычной игре. Подкласс измеряет выбранные методы
через `Time.get_ticks_usec`; выводит среднее и p95, а не критерий прохождения CI.

## Приоритеты следующих изменений

1. **HUD и поиск взаимодействия.** `_update_hud` вызывает `interaction.current`
   несколько раз, мобильная раскладка делает ещё один поиск. `current` перебирает
   collectibles/предметы и проверяет перекрытие деревьями, камнями, рельефом.
   Вычислять визуальную цель один раз за кадр после камеры, передавать результат
   HUD/крестику/контекстной кнопке. При нажатии пересчитывать цель, чтобы не
   активировать устаревший предмет. Обновлять скорость и текст HUD 10–15 Гц,
   менять строки только при изменениях, миникарту перерисовывать только когда
   видима. Прицел и камера остаются покадровыми. Проверять корректность после
   сбора/переноса предмета, открытия багажника и смены режима.
2. **Пространственный индекс камней и предметов.** `stage.rock_hit` линейно
   перебирает все камни; `crowd_navigation.context` тоже проходит весь список.
   У деревьев уже есть `tree_cells` — повторить подход для камней/collectibles,
   выбирая клетки по swept AABB с радиусом и максимальным размером объекта.
   Сохранять точную проверку, earliest contact, escape из пересечения и обновлять
   индекс для подвижных препятствий. Проверять прыжки, скорость, края клеток,
   деревню, рендерные FPS и сетевой prediction.
3. **Навигация зрителей.** На каждого зрителя каждый кадр строится контекст
   препятствий и проверяется маршрут. A* ограничен двумя планами *на кадр*:
   при 60 FPS допустимая частота планов тоже растёт. Ввести бюджет по времени/
   секунде, очередь и распределение обновлений между зрителями. Решения AI
   обновлять реже, движение/анимацию интерполировать; реакцию на близкую машину
   сохранять немедленной. Не отключать авторитетную симуляцию далёких NPC хоста.
4. **Изменяемая декорация.** `stage.update_fallen` продолжает записывать
   MultiMesh transforms после завершения падения (age=1.3). Обновлять только
   ещё падающие деревья; хранить конечное положение для коллизий и snapshot.
   `foraging.update_visuals` повторно устанавливает порции/стиль грибов каждый
   кадр — заменить обновлениями при изменении состояния и сетевом snapshot.
5. **Выделения памяти и сеть.** Мобильный `_layout` каждый кадр заново создаёт
   массив словарей кнопок; перестраивать при размере/режиме/изменении доступных
   действий. Кэшировать ссылки на конечности аватаров вместо покадрового поиска
   узлов. Гравий сейчас создаёт/удаляет узлы — пул после проверки профилем во
   время гонки. Не увеличивать частоту sync с FPS; отдельно измерять сериализацию
   world_state и обработку snapshots на хосте с 8 игроками.

В исходном MR33 изменён лимит и добавлен инструмент измерения.
Результаты последующей реализации приведены ниже. Для каждого изменения нужны одинаковый
сценарий до/после, время CPU среднего/p95/p99, memory и регрессии поведения.

Официальные рекомендации:
- https://docs.godotengine.org/en/4.4/classes/class_engine.html#class-engine-property-max-fps
- https://docs.godotengine.org/en/4.4/tutorials/performance/cpu_optimization.html

## Реализовано: HUD и локальный поиск предметов

HUD сравнивает снимок отображаемых значений до формирования строк. При
совпадении пропускает их построение; каждое свойство Label дополнительно
записывается только при изменении окончательной строки. Скорость сравнивается
в целых км/ч, состояние машины в целых процентах, countdown в целых секундах.
Мобильный скрытый таймер elapsed не вызывает перестроение. Прогресс
отрезвления остаётся непрерывным, потому что его полоса реально меняется.

Цель прицела вычисляется один раз при обновлении HUD после камеры и движения;
тот же результат используется мобильной кнопкой в текущем process frame.
Поиск цели остаётся покадровым независимо от неизменности HUD, чтобы реагировать
на движение камеры, машины и предметов. При нажатии interaction.activate
по-прежнему вызывает current заново: визуальная подсказка не выдаёт право
взаимодействовать с уже убранным или закрытым объектом.

Грибы/ягоды/виноград индексируются в клетках 8×8 м. Проверяются кандидаты
из клеток вокруг игрока, затем прежние точные проверки досягаемости, прицела,
высоты и перекрытия. ID и порядок генерации сохранены; harvest не меняет индекс.
Изменение числа предметов перестраивает индекс. Позиции generated collectibles
статичны; при их ручном перемещении/замене массива с тем же размером необходимо
сбросить indexed_collectible_count=-1. Этот случай не используется в игре.

Миникарта перерисовывается только при видимости, максимум 10 раз/с.
У завершивших падение деревьев transforms больше не записываются повторно;
изменение age/direction в snapshot всё равно обновляет их, в том числе при
позднем подключении. Коллизии и финальный basis сохраняются.

### Повторный замер до/после

Два последовательных запуска того же инструмента, Godot 4.4.1 headless,
лесной СУ, 30 кадров прогрева + 300 замеров в каждом режиме. Для обоих запусков
rng игры фиксирован seed=20261008. Физика/сетевая частота и лимит FPS одинаковы.
Не было параллельного запуска тестов во время этих замеров.

| Метрика пешком | До, среднее / p95, мс | После, среднее / p95, мс |
|---|---:|---:|
| HUD, включая поиск цели | 4.55 / 7.63 | 0.29 / 0.54 |
| `game._process` | 10.92 / 16.35 | 7.10 / 10.16 |

Среднее время HUD уменьшилось примерно на 94%, `_process` — на 35%.
Это один контролируемый сценарий, не гарантия аналогичного выигрыша в гонке,
деревне, мультиплеере или VK WebView. Изменения GPU и полного времени кадра
не измерены. Пространственный индекс **камней**, бюджет навигации NPC, пул
гравия и обновления мангала по событиям остаются отдельными следующими шагами.

Проверки покрывают неизменный HUD, округление скорости/таймера, смену цели и
состояния еды, показ/исчезновение mobile toast, границы клеток, harvest и
перестроение индекса, late snapshot и смену направления упавшего дерева.
