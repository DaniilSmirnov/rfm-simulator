# Тестовые покупки VK: зимний СУ

Реализован только тестовый режим для `stage_02` («Зимний Турини»).
`get_item` и `get_item_test` возвращают описание товара без выдачи прав.
Обычный `order_status_change` отклоняется. В конфигурации включён
режим `test`, список тестеров `*`: кнопку видят подтверждённые пользователи VK.
Боевые платежи не поддерживаются. Возможность провести именно тестовый платёж
также должна быть включена в кабинете VK.

## Включение после проверки настроек приложения

1. Развернуть Worker с миграцией `v2`. Она создаёт отдельный SQLite-backed
   Durable Object `VkPayments`, binding `PAYMENTS`. Дополнительная D1 БД не нужна.
   Комнаты продолжают использовать `ROOMS`. Платёжное хранилище не имеет TTL
   или удаления по завершении выезда. Не удалять namespace и миграцию при обновлениях.
2. В `wrangler.jsonc` установить `VK_PAYMENTS_MODE: "test"`,
   `VK_PAYMENTS_TEST_USERS: "*"` (кнопка для всех подтверждённых пользователей VK),
   либо перечислить числовые VK ID через запятую для ограничения доступа,
   `VK_STAGE_02_TEST_PRICE: "1"` — целое количество голосов.
   Проверить `VK_APP_ID` и существующий серверный secret `VK_APP_SECRET`.
   Не помещать secret в код, клиент, URL или отчёт об ошибке.
3. В настройках приложения `54809523` указать HTTPS callback
   `https://<домен-игры>/api/vk/payments/callback`.
   В кабинете VK отдельно включить тестовые платежи и доступ тестеров.
   Bridge вызывается с `{type: "item", item: "stage_02"}`: параметра
   `test_mode` у этого вызова нет. Одного серверного флага недостаточно,
   чтобы превратить реальный платёж VK в тестовый.
4. Открыть игру через VK аккаунтом тестера, выбрать зимний СУ.
   Цена в кнопке и callback совпадает. Не менять цену во время тестовой покупки.
   После callback СУ становится доступен для создания комнаты.

Официальный пример VK связывает `VKWebAppShowOrderBox` с настройкой callback:
https://github.com/VKCOM/vk-direct-games-example#внутриигровые-покупки
Ссылки на спецификацию: https://vk.com/dev/payments_callbacks и
https://vk.com/dev/payments_example . Эти страницы оказались недоступны при
реализации. Обработчик следует контракту Payments API с form-urlencoded
`sig` (MD5 отсортированных `key=value` без `sig` + secret), тестовыми
уведомлениями и состоянием `chargeable`. Перед включением в кабинете требуется
сверить контракт с доступной актуальной документацией VK и проверить настоящий
тестовый callback. Автоматические тесты используют синтетические уведомления;
они не подтверждают доступность платежей конкретному приложению или платформе.

## Контракт и хранение

- `get_item` / `get_item_test`: подписанные `app_id`, `user_id`, `item=stage_02` →
  `{response:{item_id:"stage_02",title,photo_url:"",price}}`; права не выдаются.
- `order_status_change_test`: подписанные `app_id`, `user_id`, `order_id`,
  `item=stage_02`, `item_id=stage_02`, `item_price=<цена>`, `status=chargeable`. Подарки другим аккаунтам
  не поддерживаются. Цена, ID и режим проверяются сервером.
- Транзакция записывает заказ, аккаунт и `entitlements:test:<user>` вместе.
  Receipt `{order_id,app_order_id}` хранится и повторяется без новой выдачи.
  Повтор с другим владельцем/товаром/суммой отклоняется. Ошибка хранилища
  возвращает `critical:false`; подтверждение не отдаётся до commit.
- Права привязаны к подтверждённому VK ID. Тестовые права видны только
  разрешённым пользователям при `VK_PAYMENTS_MODE=test`; `*` разрешает все
  корректные VK ID, числовой список ограничивает доступ. При выключении скрываются,
  но сохраняются. Боевого хранилища/боевых продаж в этой реализации нет.
- `/api/vk/store` и `/api/vk/payments/prepare` требуют Bearer-сессию.
  Клиент не может передать права доступа серверу. Создание комнаты и выбор
  личной машины проверяются по правам из хранилища.
- Bridge сообщает только результат окна. Даже после `success` игра ждёт
  серверные права. После ошибки/отмены права перепроверяются, после задержки
  доступны «Проверить покупку», восстановление фокуса и новый запуск.

## Приёмка в VK

Проверить desktop, Android и iOS: открыть окно и отменить; завершить тестовый
заказ; дождаться callback; создать комнату на зимнем СУ; перезапустить игру
и Worker; убедиться, что доступ сохранился. Повторить callback с тем же
`order_id`: ответ идентичен. Аккаунт вне списка и боевое уведомление не должны
получать товар (для проверки списка заменить `*` на конкретные ID).
Для выключения покупок установить `VK_PAYMENTS_MODE: "disabled"` и развернуть
Worker заново; сохранённые тестовые права не удаляются. Подключение боевых продаж — отдельная задача.

Автопроверки: `npm run test:vk`, `npm test`, `npm run test:server` (реальный
локальный Worker / SQLite-backed Durable Object, включая его перезапуск).

## Если VK сообщает «Поддерживаются только тестовые уведомления»

`get_item_test` и `order_status_change_test` уже содержат нужный суффикс.
Не добавлять `_test` повторно и не заменять его префиксом `test_`.
Запрос `get_item_test` с полями `order_id`, `receiver_id`, `lang` поддерживается;
для подписи используются все полученные параметры, включая эти поля.

У актуального обработчика каждый ответ имеет заголовок
`X-Rally-Payments-Handler: vk-test-callback-v4`.
Если тип не поддерживается, `error_msg` содержит фактический `notification_type`
и тот же маркер версии. Ошибка также попадает в логи Worker без сырого тела,
подписи и секретов. Старый текст без типа и маркера означает ответ старой
версии или другого endpoint. Проверить URL в кабинете VK и завершение именно
production-деплоя; слияние MR само по себе не подтверждает успешный деплой.
Не использовать URL preview-версии Worker для постоянных уведомлений.


В отчёте VK встречено расхождение: в отображаемом запросе `get_item_test`,
а подписанный запрос, разобранный Worker, содержит `get_item`. Причина
расхождения не установлена. Оба варианта получения описания поддерживаются
без изменения параметров до проверки подписи. Это не включает боевые продажи:
выдача прав возможна только через `order_status_change_test`. Если следующим
уведомлением придёт `order_status_change`, нужно проверить тестовый режим VK,
а не добавлять суффикс на сервере.


Обработчик v4 соответствует фактическому тестовому заказу VK: `item_id`
равен SKU `stage_02`, цена передаётся в `item_price`. Старые числовой ID `2`
и поле `amount` также поддерживаются; конфликтующие цены или SKU отклоняются.
Остальные подписанные поля (`date`, `item_title`, `item_photo_url` и др.)
участвуют в проверке подписи. Выдача остаётся атомарной и идемпотентной.
